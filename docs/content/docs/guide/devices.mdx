You never construct a [`Device`](/docs/client/device) yourself. The client creates instances when the server reports hardware, then exposes them through events and `client.devices`.

```ts
client.on("device.added", ({ data: { device } }) => {
  console.log(device.index, device.displayName ?? device.name);
  console.log(device.features);
});

await client.startScanning();
```

## Discovery workflow

<Steps>
  <Step>
    ### Start scanning

    ```ts
    await client.startScanning();
    ```

    Emits `scan.started`. The server searches configured backends (Bluetooth, serial, HID, etc.).
  </Step>

  <Step>
    ### Handle new devices

    Each discovery emits `device.added` with a ready-to-use `Device`:

    ```ts
    client.on("device.added", ({ data: { device } }) => {
      console.log(`Added #${device.index}: ${device.name}`);
    });
    ```
  </Step>

  <Step>
    ### Stop scanning (optional)

    ```ts
    await client.stopScanning();
    ```

    Scanning also ends when the server finishes (`scan.finished`). **Devices remain listed** after the scan stops.
  </Step>
</Steps>

<Callout type="info">
  With [`WasmTransport`](/docs/guide/wasm#scanning-behavior), `startScanning()` opens the browser's Bluetooth picker (one device per call). `scan.finished` fires when the picker closes, often before `device.added`. `stopScanning()` is a no-op.
</Callout>

### Reconciliation

`client.requestDeviceList()` asks the server for the current list and reconciles local state. Use this after reconnect or when you suspect the list is stale:

```ts
await client.requestDeviceList();
// May emit device.added, device.removed, and device.updated
// Always ends with device.list { devices }
```

## Device properties

| Property | Type | Description |
| --- | --- | --- |
| `index` | `number` | Server-assigned ID for this session |
| `name` | `string` | Firmware / internal name |
| `displayName` | `string \| null` | User-facing label from the server, if any |
| `features` | `DeviceFeatures` | Parsed `{ inputs, outputs }` arrays |

Each feature entry includes `type`, `index`, and `range` (and duration range for position actuators). Ranges come from the server and drive clamping in command methods.

```ts
for (const output of device.features.outputs) {
  console.log(
    `${output.type} feature ${output.index}`,
    `range ${output.range[0]}–${output.range[1]}`,
  );
}
```

## Capability checks

Always check capabilities before sending commands. Unsupported types throw [`DeviceError`](/docs/client/errors).

### Outputs

```ts
if (device.canOutput("Vibrate")) {
  await device.vibrate(0.5);
}

if (device.canRotate) {
  await device.rotate(0.6);
}

if (device.canPosition) {
  await device.position(0.8, { duration: 500 });
}
```

| Helper | Meaning |
| --- | --- |
| `canOutput(type)` | At least one output feature of that type |
| `canRotate` | `Rotate` or `RotateWithDirection` |
| `canPosition` | `Position` or `HwPositionWithDuration` |

Full output type list: [`OUTPUT_TYPES`](/docs/client/constants#output_types).

### Sensors

```ts
if (device.canRead("Battery")) {
  const level = await device.readSensor("Battery");
}

if (device.canSubscribe("Button")) {
  await device.subscribeSensor("Button", (value) => {
    console.log(value === 1 ? "pressed" : "released");
  });
}
```

Full input type list: [`INPUT_TYPES`](/docs/client/constants#input_types).

See [Sensors](/docs/guide/sensors) for read vs subscribe semantics.

## Lifecycle events

| Event | Meaning |
| --- | --- |
| `device.added` | New hardware in the session |
| `device.removed` | Hardware disconnected or client reset |
| `device.updated` | Metadata changed (`displayName`, features, …) |
| `device.list` | Full list after reconciliation |

On client disconnect, every device is removed locally before `connection.disconnected`.

## Lookup by index

```ts
const device = client.getDevice(0);
if (device) {
  await device.stop();
}
```

`client.devices` is a read-only array of all known devices.
