[`ButtplugClient`](/docs/client/buttplug-client) extends [Emittery](https://github.com/sindresorhus/emittery) with a typed [`ClientEventMap`](/docs/client/types#clienteventmap). Event names use dot namespaces (`device.added`, `connection.disconnected`, …).

```ts
const unsub = client.on("device.added", ({ data: { device } }) => {
  console.log(device.name);
});

unsub();
```

Emittery v2 passes `{ name, data }` to listeners. Destructure `data` for the payload.

## Registering listeners

```ts
// Every occurrence
client.on("scan.finished", () => {
  console.log("Scan done");
});

// Once
await client.once("connection.connected");
```

Register handlers **before** `connect()` if you need to observe the full session from the first device onward.

## Connection events

| Event | Payload | When |
| --- | --- | --- |
| `connection.connecting` | none | `connect()` started |
| `connection.connected` | none | Handshake complete |
| `connection.disconnected` | `{ reason?: string }` | Transport closed |
| `connection.reconnecting` | `{ attempt: number }` | WebSocket reconnect attempt |
| `connection.reconnected` | none | Session restored after reconnect |
| `connection.error` | `{ error: Error }` | Transport or non-device protocol error |

[Connecting](/docs/guide/connecting) covers reconnect and ping behavior.

## Device events

| Event | Payload | When |
| --- | --- | --- |
| `device.added` | `{ device }` | Hardware discovered |
| `device.removed` | `{ device }` | Hardware gone or list cleared |
| `device.updated` | `{ device, previousDevice }` | Metadata or features changed |
| `device.list` | `{ devices }` | After `requestDeviceList()` reconciliation |
| `device.error` | `{ error: ProtocolError }` | Server push with `ErrorCode.DEVICE` |

<Callout type="info">
  Command failures (`device.vibrate()` rejecting) do **not** emit `device.error`. They reject the promise. `device.error` is for asynchronous server-side device errors.
</Callout>

## Scan events

| Event | When |
| --- | --- |
| `scan.started` | `startScanning()` accepted |
| `scan.finished` | Server finished scanning |

With [`WasmTransport`](/docs/guide/wasm#scanning-behavior), `scan.finished` fires when the browser's Bluetooth picker closes, usually **before** the matching `device.added`. Don't gate "scanning…" UI on these two events alone.

## Input events

| Event | Payload | When |
| --- | --- | --- |
| `input.reading` | `{ reading }` | Server pushed a sensor value |

See [Sensors](/docs/guide/sensors) for `subscribeSensor` vs this global event.

## Typical session timeline

```
connection.connecting
connection.connected
scan.started
device.added          (× N devices)
device.list           (after reconciliation, if requested)
scan.finished
… user commands …
device.removed        (hardware unplugged)
connection.disconnected
```

### After reconnect (`autoReconnect`)

1. `connection.disconnected`
2. `device.removed` for each cached device
3. `connection.reconnecting` (per attempt)
4. `connection.reconnected`
5. Fresh `device.added` / `device.list` for hardware still connected

Re-apply any local state (selected device, running patterns) in `connection.reconnected`.

## Cleanup

```ts
client.dispose();
```

Removes all listeners and tears down internal subscriptions. Prefer unsubscribing individual handlers when the client stays alive:

```ts
const off = client.on("connection.error", ({ data: { error } }) => {
  console.error(error);
});
off();
```
